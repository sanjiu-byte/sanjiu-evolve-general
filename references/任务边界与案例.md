# 任务边界与案例

开工与每次实质修改时使用。依据当前使用者和项目的真实要求理解边界，案例用于说明机制，不预设任何行业风格、交付格式或审美。

## 三类边界

从当前权威要求与本轮请求中取出影响决策的部分。有持续任务记录就更新原记录，否则在当前上下文核对即可，不另建三套规则库，也不要求员工填表。

| 类别 | 应表达的内容 |
| --- | --- |
| 必须做到或保留 | 具体成果、正确性条件、关键信息、仍有效的已确认内容；偏好另标优先，不一律当硬约束 |
| 禁止或未经允许不改 | 有明确来源的禁止事项、保留内容、修改范围及其适用条件 |
| 可以自行优化 | 为实现目标可自主选择的表达、组织或实现细节，说明关键自由度即可 |

保留关键原话或准确定位、适用范围、强度和确认状态。使用者跨项目默认、当前项目约定、本次例外分别使用。暂行经验保留暂行状态，不能升级为确认禁令。当前明确变更只替换相应范围，其余有效要求继续保留；与客户已确认边界冲突且变更权限不清时，先做无冲突部分，澄清关键取舍。

自主范围不是封闭白名单。未列出的常规细节可以按目标判断，不逐字问许可；它也不产生额外读取私人资料、上传发布或保存对话的权限。内容取舍与操作授权分别核对。“不记”时不另外保存清单、摘要或日志。

## 防止长对话把要求改没了

每次实质修改前，从当前权威正文或任务记录核对三个问题：

1. 本轮明确改变什么？
2. 其他哪些关键要求仍有效？
3. 依据哪一版成果，哪些部分已确认，哪些仍在探索？

保留少量关键要求原文或可准确回查的定位。完整方法未变时无需每轮全文读取，但不能以“之前读过”替代本轮核对，也不能把多轮摘要的再摘要当权威要求。遇到缺项、冲突或加载状态不明就回到来源。

局部调整以指定基线为准，直接修改需要改的部分；能用差异比较或适用检查工具时核对范围外变化，避免自由重写整份成果。工具只能检查其覆盖的条件，含义、适用范围和目标是否落实仍需判断。全文重构可以改变结构，但未被替换的有效要求仍需核对。

完成后将改变项与保留项对应到成果具体位置，检查遗漏、越界改动以及过度冻结允许的变化。不能为了通过检查把全文都标成可改，也不能因旧例限制当前明确允许的改写。能修先修；确实存在不可兼得时说明具体取舍。无需每次展示内部清单，不以清单完整或多 AI 同意代替成果核验。

## 从真实项目选案例

获准回顾历史时，先确认允许项目、排除范围和可访问材料，沿同一任务的前版→反馈→后版→后续决定查证。后续决定可能改变此前状态；不能只用最后一份助手输出当标准答案。未取得附件或完整上下文时列缺项，不补造用户意见或实际使用效果。

| 状态 | 依据与用法 |
| --- | --- |
| 明确认可 | 使用者明确选用、确认或把该版本投入指定用途，可作该条件下正例；不代表实际效果已经验证 |
| 推定接受 | 仅当该使用者明确约定了某种接受信号，且实际符合、无较新否定时使用；带状态作参考，不当明确批准或长期偏好 |
| 明确否定 | 有真实否定、作废决定或具体问题；有理由才提炼质量反例，不能臆测原因 |
| 状态不明 | 未选候选、没有后续、上下文缺失或只有 AI 自称满意；不自动作为正例或反例 |

本方法没有“换话题、没再追问就算接受”的默认。局部认可不批准整份成果，局部否定也不否定其余部分；未选候选不自动成为失败案例。接受成果不等于授权发布、确认事实或允许传播给其他使用者。明确排除学习的项目不进入正反例库。

## 合成对照：理解边界，不预装经验

以下全部为机制演示用合成情境，不是员工实测，不是使用者已确认规则。只按当前问题选择相关例子，不因读到例子就写入经验。

### 局部修复

- 情境：用户要求修复表单不能提交的问题，明确保持现有页面布局。
- 反向做法：修复提交逻辑时顺便重做布局，解释为更现代。
- 合适方向：处理提交故障，核对布局相关差异；若根因确实涉及布局，说明依赖并仅改必要部分。
- 原因：工作价值由当前目标和修改边界决定，额外变化可能增加返工。以后用户明确要求重做布局时，应允许对应改变。

### 精简交付

- 情境：项目报告已确认要保留数据来源和关键风险，本轮要求更简短。
- 反向做法：删除来源与风险，只留下结论。
- 合适方向：压缩重复解释和非关键细节，保留结论所需依据及已确认风险。
- 原因：篇幅要求没有替换原有信息要求。若用户明确只要一个供导航的标题，则按该次用途交付，不强塞整份报告。

### 新增要求

- 情境：第一版只要求统计销售额，第二轮新增退款率分析。
- 反向做法：把首版没有退款率标为 AI 漏要求，并记录为永久必查项。
- 合适方向：按新需求补充分析，保留新增发生时间；是否以后都要，按使用者明确范围判断。
- 原因：新目标可以形成经验，但不能倒算成先前错误，单次需要也不是所有报表的固定结构。

### 有条件的负反馈

- 情境：用户否定一段客户通知“太冷硬”，说明客户已等候很久，同时认可其中清楚的解决时间。
- 反向做法：记成所有通知禁止简洁语气，或为了柔和删除解决时间。
- 合适方向：在这类已等待的客户通知中，补上对处境的回应，保留解决安排；其他用途按相应要求判断。
- 原因：学习的是适用条件与取舍，不能只增加负面词表或把一种语气变成所有场合的标准。

真实反馈需要形成案例时，按 [经验与接续](经验与接续.md) 更新现有条目：条件、前后差别、真实理由、保留项、接受状态及来源即可。没有真实被拒绝版本时，演示反例必须标为假设。新证据推翻旧判断就修订状态，避免无限追加相反规则。
